# Icebreak 33 Question Design Scenario Mapping Plan

## 目的

Icebreak 33 / レボリスト診断の設問を、単なる自己評価ではなく、回答者が日常場面を楽しく選びながら、自分の持ち寄り方が自然に見える設計へ進める。

今回の方針では、設問を次のように扱う。

```text
1つの設問は、1つの役割だけを測るものではない。
すべての回答が、どれかの役割・クラスター・発動状態の手がかりになる。
```

そのため、`YESならAタイプ、NOなら関係なし` という設計にはしない。強くYES、ややYES、中間、ややNO、強くNOのすべてに意味を持たせる。

## 背景

現在の `src/data/icebreakQuestions.ts` は、11役割それぞれ3問ずつ、合計33問で構成されている。各設問は `role` / `force` / `weights` を持ち、5段階回答を軸スコアへ反映する。

この構成は最小診断として成立しているが、質問文は「自分はそういう人か」を答える自己評価に寄りやすい。今後、レボリスト診断をより自然で楽しい体験にするには、設問を次の方向へ変える必要がある。

```text
性格を直接聞かない。
心理的な意図を見せない。
日常場面の中で、自然にどこへ目が向くかを選んでもらう。
```

## 設問設計の基本思想

レボリスト診断では、誰かだけが特別なのではなく、すべての人が自分の役割に出逢ったときに力を発揮するという前提を持つ。

そのため設問も、回答によって優劣をつけるものではなく、次を読むための入口にする。

```text
- 何を自然に受け取る人か
- 何に変換したくなる人か
- 誰や場にどう届けたくなる人か
- どの役割を持ち寄りやすい人か
- その力を今どの状態で使っているか
```

## 避ける設問

次のような質問は、診断意図が見えやすく、自己評価や理想像に寄りやすい。

```text
あなたは創造的ですか？
あなたは共感力が高いですか？
あなたは論理的ですか？
あなたは新しいことが好きですか？
あなたは人のために動きますか？
あなたは自分を犠牲にしがちですか？
```

これらは答える側が「良さそうな答え」を想像しやすい。結果として、診断がその人の自然な持ち寄り方ではなく、理想自己や社会的に望ましい像に寄る可能性がある。

## 目指す設問

設問は、心理特性ではなく場面で聞く。

```text
ある場面で、あなたならどこに目がいくか。
何が気になるか。
何を放っておけないか。
何を自然にしたくなるか。
```

回答者は診断されている感覚ではなく、日常の中で自分に近い選択をしている感覚で進められるのが理想である。

## 場面選択式を基本にする

今後の候補として、5段階同意だけではなく、場面選択式を増やす。

例:

```text
Q. みんなで新しい企画を考えることになりました。
最初にあなたが見たくなるのは？

A. それがどんな未来につながるか
B. 誰が一緒に動けそうか
C. どんな順番なら進めやすいか
D. 今ある情報で何が分かるか
E. 場の空気が前向きかどうか
```

この設問は、表面上は楽しい選択に見える。しかし裏側では、複数の役割へスコアを入れられる。

```text
A: 創発 / レボリスト / マックスデザイナー / クレイジスト
B: 共感・循環 / コミュニケーター / ムーブメンター
C: 実装・場づくり / アレンジャー / プルミエルクラフター
D: 翻訳・構造化 / インフォレイダー / ロジカルマイスター
E: 共感・循環 / ソウルオーナー
```

## すべての回答に意味を持たせる

1つの設問は、表の意味だけでなく、裏の意味も持つ。

例:

```text
Q. 場にまだない可能性や違和感に、先に気づくことがある。
```

この設問で強くYESなら、創発クラスターが見える。一方でNOは、創発がないという意味ではない。

```text
強くYES:
クレイジスト / レボリスト / マックスデザイナー

ややYES:
レボリスト / イメージマイスター / マックスデザイナー

中間:
インフォレイダー / ロジカルマイスター

ややNO:
アレンジャー / プルミエルクラフター

強くNO:
ソウルオーナー / コミュニケーター
```

NOは「まだないものを見るより、今ある人・場・情報・流れを大切に見る」という別の持ち寄り方を示す。これは不足ではなく、別の入口である。

## 設問マッピングの推奨仕様

将来的な設問定義では、次のように各回答値ごとの意味を持たせる。

```text
質問番号
質問文
場面カテゴリ
主に見ているクラスター
主に見ている役割
5のとき加点する役割・軸
4のとき加点する役割・軸
3のとき加点する役割・軸
2のとき加点する役割・軸
1のとき加点する役割・軸
発動状態への影響
注意する誘導感
```

ポイントは、回答値が低い場合も別の役割へ意味を持たせることである。

```text
5 = 表の力が強く出ている
4 = 表の力が自然に出やすい
3 = 受け取ってから動く、または場面依存
2 = 別の入口を優先しやすい
1 = 反対側の持ち寄り方が見えやすい
```

## 4クラスターとの関係

今後の設問は、次の4クラスターを直接聞くのではなく、場面の中で自然に見えるようにする。

```text
創発クラスター
翻訳・構造化クラスター
実装・場づくりクラスター
共感・循環クラスター
```

### 創発クラスターを見る場面

直接聞かない表現:

```text
あなたは創造的ですか？
```

場面で聞く表現:

```text
まだ誰も言葉にしていない違和感や可能性に、先に気づくことがある。
前例がないことでも、「これは未来につながる」と感じると動きたくなる。
今ある選択肢だけではなく、別の可能性を考えてしまう。
```

### 翻訳・構造化クラスターを見る場面

直接聞かない表現:

```text
あなたは論理的ですか？
```

場面で聞く表現:

```text
誰かの感覚的な話を、他の人にも伝わる言葉に整理したくなる。
複雑な話を聞くと、自然に構造や順番を考えている。
情報が散らばっていると、判断しやすい形にまとめたくなる。
```

### 実装・場づくりクラスターを見る場面

直接聞かない表現:

```text
あなたは実行力がありますか？
```

場面で聞く表現:

```text
良いアイデアを聞くと、「どうすれば実際に動くか」を考え始める。
人や役割がバラバラなとき、自然に配置や流れを整えたくなる。
誰かが一歩踏み出せるように、具体的なきっかけを渡したくなる。
```

### 共感・循環クラスターを見る場面

直接聞かない表現:

```text
あなたは共感力が高いですか？
```

場面で聞く表現:

```text
場の中で、話せていない人や安心できていない人に気づきやすい。
人と人の間に会話の入口を作ることが自然にある。
誰かの本音や小さな変化を、言葉になる前に感じ取ることがある。
```

## 発動状態も直接聞かない

発動状態を見る場合も、重い言葉をそのまま使わない。

避ける表現:

```text
あなたは自分を犠牲にしがちですか？
あなたは自己超越していますか？
あなたは承認欲求が強いですか？
```

場面で聞く表現:

```text
Q. イベントの準備で、予定よりやることが増えてきました。
あなたに近い動きは？

A. まず自分で巻き取って、なんとか形にする
B. できることと頼めることを分ける
C. 得意そうな人に声をかけて、持ち寄れる形にする
D. 一度立ち止まって、無理なく続く形を考える
E. みんなが疲れていないか様子を見る
```

裏側では、次のように読む。

```text
A: ひとりで抱えやすい
B: 回復・整理
C: 持ち寄り化
D: 持続設計
E: 共感・循環
```

ただし、Aを悪く扱わない。Aは「責任感が強く出やすい」「まず形にしようとする」入口として扱い、結果表示では自分を削らない持ち寄り方へ案内する。

## 楽しく選びやすい設問のルール

設問は、回答者が悩みすぎず、直感で進められることを優先する。

```text
- 1問を長くしすぎない
- 選択肢の良し悪しが見えないようにする
- どの選択肢も魅力的に見せる
- ネガティブなラベルを置かない
- 心理用語を使わない
- 日常・会話・イベント・チーム場面に寄せる
- 「あなたは〇〇ですか？」より「この場面なら何を見る？」にする
```

回答者の体験としては、診断されているよりも、軽いシミュレーションを進めている感覚が望ましい。

## 設問カテゴリ案

今後の33問または次版診断では、次のような場面カテゴリを使う。

```text
1. 新しい企画が始まる場面
2. 誰かが相談してきた場面
3. チームが止まっている場面
4. 場の空気が重くなった場面
5. アイデアが出すぎてまとまらない場面
6. 良いものを最後まで磨く場面
7. 人と人をつなぐ場面
8. 違和感を感じた場面
9. 未来を考える場面
10. イベント当日の動き
11. 誰かの想いを受け取る場面
12. 役割が足りない場面
```

これらの場面で、11役割のどれが自然に出るか、また別の回答ではどの役割が見えるかを設計する。

## サンプル設問

### 企画が始まる場面

```text
Q. 新しい企画の話が出たとき、最初に気になるのは？

A. それがどんな未来につながるか
B. 誰が一緒に動けそうか
C. どんな順番なら進めやすいか
D. 今ある情報で何が分かるか
E. 場の空気が前向きかどうか
```

### 誰かがまだ言葉にならない想いを話している場面

```text
Q. 誰かが「まだうまく言えないけど、こういうことをやりたい」と話しています。
あなたが自然にしたくなるのは？

A. その中にある未来の種を一緒に広げる
B. 言葉にして、他の人にも伝わる形にする
C. まず小さく試せる一歩を考える
D. その人が安心して話せるように聞く
E. 必要な人や情報をつなぐ
```

### アイデアが多く出た場面

```text
Q. みんなからアイデアがたくさん出て、少し散らかってきました。
あなたがやりたくなるのは？

A. もっと面白い可能性がないか広げる
B. 似ている案をまとめて、伝わりやすくする
C. 実際に試せる順番へ並べる
D. 誰の持ち味がどこで活きるかを見る
E. 置いていかれている人がいないかを見る
```

### イベント準備が増えてきた場面

```text
Q. イベントの準備で、予定よりやることが増えてきました。
あなたに近い動きは？

A. まず自分で巻き取って、なんとか形にする
B. できることと頼めることを分ける
C. 得意そうな人に声をかけて、持ち寄れる形にする
D. 一度立ち止まって、無理なく続く形を考える
E. みんなが疲れていないか様子を見る
```

## 現行33問への適用方針

現行の33問をすぐ差し替えない。まずは次の順で進める。

```text
Phase 1:
現行33問を、自己評価型 / 場面型 / 誘導感あり / 中立の4分類で監査する。

Phase 2:
各設問について、回答値1〜5がどの役割・軸に意味を持つかを表にする。

Phase 3:
自己評価型で誘導感が強い設問から、場面選択式へ置き換える候補を作る。

Phase 4:
検証フォームまたは別版テストで、場面選択式の回答しやすさを確認する。

Phase 5:
本診断の設問・スコアリングへ反映する。
```

## 実装設計上の注意

将来的に実装する場合、既存の `icebreakQuestions` をそのまま置き換えるのではなく、次版の設問型を別に設計するのが安全である。

候補:

```text
src/data/icebreakScenarioQuestions.ts
src/lib/calculateIcebreakScenarioResult.ts
```

既存の `calculateIcebreakResult.ts`、`centeredResult`、検証フォーム、オフ会参加保存はすでに本番利用されているため、いきなり置き換えない。

まずは現行33問と並走できる形で、検証用として扱う。

## 結論

次の段階の設問では、質問の質を次の方向へ上げる。

```text
心理特性を直接聞かない。
日常場面で聞く。
全部の選択肢を魅力的にする。
どの回答にも役割としての意味を持たせる。
NOを不足ではなく、別の持ち寄り方として読む。
発動状態も重い言葉ではなく、自然な行動として見る。
```

これにより、Icebreak 33 は `あなたはどんな性格か` を当てる診断ではなく、`あなたは場の中で何を受け取り、何に変換し、何を持ち寄る人か` を読む診断へ進める。

# Icebreak 33 Diagnosis Experience Audit

## 目的

Icebreak 33 / レボリスト診断は、オフ会運営者向けにイベント作成、参加者URL、参加者自動登録、host画面、席順保存、role-aware seating まで動く状態になっている。

一方で、本番確認では「診断結果として自分が11役割の何なのかが見えにくい」「席順が11役割マッチングとして体感しにくい」「設問に誘導感があるかもしれない」という体験面の違和感が残っている。

このdocsでは実装を変更せず、現在の結果表示、席順ロジック、設問、11役割判定を監査し、改善順を整理する。

## 総合結論

現状は機能としては動いている。organizerでイベントを作成し、participantUrlから診断し、参加者が保存され、hostUrlで参加者と席順を確認できる土台は成立している。

ただし、診断体験としては11役割の見え方がまだ弱い可能性がある。内部では `mainTypeKey` / `partnerTypeKey` / `centerForce` が計算されているが、結果ページ上部では「あなたは〇〇タイプです」と一目で言い切る構成ではなく、`centerForce` のカードも目立つため、参加者が自分の11役割を名札のように使いにくい。

オフ会で使うなら、結果ページに「自分の11役割」が明確に出る必要がある。さらに「可能性を引き出し合いやすい相手」「自己紹介に使える一言」「なぜこの役割になったか」を短く見せると、参加者同士の会話材料になりやすい。

席順は role-aware 化されているが、体感として伝わる表示・理由文が必要である。APIは `generateIcebreakRoleAwareSeating` を使い、`mainTypeKey` / `partnerTypeKey` を渡している。しかしhost画面の参加者表示やテーブル見出しはまだ5つの力が中心に見えるため、11役割マッチング感が画面上で伝わりきっていない。

設問は11役割それぞれ3問ずつで役割数のバランスは取れている。一方、質問文は全体的に肯定しやすい表現が多く、社会的に望ましい回答へ寄りやすい可能性がある。修正は一括ではなく、結果表示 → 設問監査 → 席順理由表示 の順で進めるのが安全。

## A. 結果表示で11役割が分かるか

### 現状

`IcebreakResultClient.tsx` は `calculateIcebreakResult` と `getIcebreakResultDetails` を使って結果を表示している。内部的には `mainTypeKey`、`partnerTypeKey`、`centerForce`、`subForce`、`roleScores` が算出されている。

結果ページ上部には `details.title` が大きく表示される。通常時の見出しは `〇〇の入口が出ています` という形で、11役割名そのものを「あなたは〇〇タイプです」と明示する構成ではない。低確信度時には「まだ役割をひとつに絞らない入口です」となる。

11役割コピーは `icebreakRoleResultCopy.ts` の `workingCopy` や `catchCopy` として表示されている。これは会話の素材として使えるが、最初の視線で「自分の11役割」が確定的に見える設計ではない。

`centerForce` は独立したカードで目立つ。5つの力は補助情報として有用だが、現在の画面構成では11役割よりも「入口の力」が強く印象に残る可能性がある。

`partnerTypeKey` は「今日、つながると動き出す人」として表示される。これはオフ会用途に近いが、主表現としては少し行動開始に寄る。結果ページでは「可能性を引き出し合いやすい相手」を第一候補にし、自分の役割と相手の役割を一言で説明できる自己紹介文へつなげるのがよい。

### できていること

- `mainTypeKey` / `partnerTypeKey` は内部で計算されている
- 11役割別のコピー、自己チェック、会話の入口が用意されている
- 「今日、つながると動き出す人」として相手候補が表示される
- 低確信度時に役割を無理に固定しない配慮がある

### できていないこと

- 結果ページ上部で「あなたの11役割」が一目で分かりにくい
- `centerForce` が11役割より目立つ可能性がある
- 5つの力と11役割の関係説明が短い
- オフ会でそのまま読める自己紹介文が不足している
- 「なぜこの役割になったのか」の説明が弱い

### 改善案

- 結果ページ上部に「あなたの11役割」を大きく表示する
- 見出しを「あなたは〇〇タイプです」に近い形へ寄せる
- 5つの力は補助情報として、11役割の下に置く
- 「可能性を引き出し合いやすい相手」を `partnerTypeKey` と関連候補から2タイプ表示する
- オフ会用の自己紹介文を追加する
- 例: `私は〇〇タイプ。得意なのは△△で、可能性を引き出し合いやすい相手は□□タイプと◇◇タイプです。`
- 上位2〜3役割を補助表示し、納得感を補う

### オフ会用自己紹介カード案

結果ページには、診断結果をそのまま会話に使える自己紹介カードとして表示する案がある。ここでは上下関係や依存関係に見えないようにし、「相手に引き出してもらう」だけではなく「お互いに持ち味を引き出し合う」表現を優先する。

主見出しの第一候補:

```text
可能性を引き出し合いやすい相手
```

より文脈を柔らかくする場合:

```text
お互いの可能性を引き出し合いやすい相手
お互いの持ち味が活きやすい相手
次の一歩が見えやすい相手
一緒に話すと、形になりやすい相手
会話のきっかけになりやすい相手
```

見出しとしては避けたい表現:

```text
話すと広がりやすい相手
相性がいい人
あなたに合う人
弱点を補う人
この人と組むべき
```

「相性がいい人」は説明文の内部で限定的に使う余地はあるが、見出しにはしない。恋愛的に見えたり、人間関係を固定する印象が出たり、レボリスト診断の「応援」「持ち寄り」「可能性を引き出す」思想が弱くなるためである。

自己紹介カードの短い表示案:

```text
今日の私は、△△タイプ。
〇〇をしている人です。

可能性を引き出し合いやすい相手は、
□□タイプ / ◇◇タイプ。
```

少し説明を含める表示案:

```text
私は、〇〇をしている人です。
今日ここに来たきっかけは、□□です。

今回の診断では、
「△△タイプ」でした。

お互いの可能性を引き出し合いやすい相手は、
「□□タイプ」と「◇◇タイプ」です。
```

表示項目案:

- ニックネーム
- 何をしている人か
- 今日ここにいるきっかけ
- あなたの11役割
- 役割の短いキャッチコピー
- 可能性を引き出し合いやすい相手 2タイプ
- `centerForce` は補助情報として表示

入力項目は次の優先順がよい。

- 必須: ニックネーム
- 任意: 何をしている人ですか？
- 任意: 今日ここにいるきっかけは？

`今日話したいこと` は初期優先度を下げる。少し硬く、初対面で答えづらい人がいるため、まずは「きっかけ」の方が自然に会話へ入りやすい。

2タイプ表示の初期方針:

- 1タイプ目: `partnerTypeKey`
- 2タイプ目: `futurePartners` または `teamCompatibility` の `best` / `good` から選ぶ

実装時に新しい判定ロジックを作りすぎず、まずは既存の `partnerTypeKey` と既存データにある相性情報を活用する。候補が重複する場合は重複を除き、本人の `mainTypeKey` と同じ役割が出る場合は別候補へ回す設計がよい。

## B. オフ会で会話しやすい結果になっているか

### 現状

結果ページには会話の入口になるコピーがあるが、参加者が隣の人に「自分は何タイプ」と説明するには、役割名と短い自己紹介文がもう少し前面に必要である。

host画面では参加者カードにニックネーム、`centerForce`、`subForce` が表示される。一方、`mainTypeKey` / `partnerTypeKey` や11役割名は見える形になっていない。運営者が「この人はどの役割か」を一覧で把握するには情報が足りない。

席順表示では、テーブル見出しに各メンバーの `centerForce` が並ぶ。role-aware seating の理由文は表示されうるが、見出しや参加者カードが5つの力中心なので、全体としてはまだ11役割マッチングよりも力の分散に見えやすい。

### 会話導線としての不足

- 参加者同士が「あなた何タイプ？」と話すための一言表示が弱い
- host画面で11役割名を把握できない
- 席順理由に11役割名が必ず出るわけではない
- 役割説明が結果ページ内に散らばり、名札として使いにくい

### 改善案

- 結果ページに「オフ会での自己紹介」ブロックを追加する
- 結果ページに「このタイプの人に聞いてみて」導線を追加する
- host画面の参加者カードに `mainTypeKey` の日本語名を表示する
- host画面に `partnerTypeKey` を「可能性を引き出し合いやすい相手」として表示する
- 席順理由に、可能な範囲で11役割名や補完関係を短く含める
- 理由文は断定ではなく「会話のきっかけ」として表現する

## C. 席順は本当に11役割マッチングになっているか

### 現状

`POST /api/icebreak/seating` は `generateIcebreakRoleAwareSeating` を使っている。保存時の `algorithm_version` は `icebreak-seating-role-aware-v1` になっている。

Supabase参加者行からは、以下が席順生成へ渡されている。

- `main_type_key` → `mainTypeKey`
- `partner_type_key` → `partnerTypeKey`
- `center_force` → `centerForce`
- `result_summary.subForce` → `subForce`
- `joined_at` → `joinedAt`
- `display_name` → `nickname`

`generateIcebreakRoleAwareSeating` は `getRoleTableScore`、`getRolePairScore`、`getRoleMatchReason` を使い、`partnerTypeKey`、`futurePartners`、`teamCompatibility`、同一 `mainTypeKey`、同一 `centerForce` をスコアに反映している。

### role-aware化できている点

- APIはrole-aware版の席順生成関数へ接続済み
- `mainTypeKey` / `partnerTypeKey` が席順生成に渡っている
- `futurePartners` と `teamCompatibility` がスコアに使われている
- 隣席理由に `getRoleMatchReason` 由来の文が入りうる
- `algorithm_version` で旧版との差別化ができている

### 体感として弱く見える可能性

- host画面のテーブル見出しは `centerForce` 表示が中心
- host画面の参加者カードに11役割名が出ていない
- 席順理由が常に11役割名を含むとは限らない
- 参加者数が少ない場合、role-awareの効果が見えにくい
- `sameForcePenalty` やテーブルサイズ調整が強く働く場面では、11役割スコアが同点調整のように見える可能性がある

### 改善案

- host画面に `algorithm_version` を確認できる内部表示またはログ観点を用意する
- host画面のテーブル見出しを `centerForce` だけでなく11役割名も併記する
- 席順理由に「なぜ近くにしたか」を短く表示する
- `centerForce` と role score の比率を参加者数別に調整する
- 2人 / 3人 / 4人卓ではペアスコアを強め、5人以上ではテーブル多様性を強める
- 理由文がhost画面で読みやすい長さになっているか本番確認する

## D. 設問バランス監査

### 全体所見

33問は11役割それぞれ3問ずつ割り当てられており、役割数としては均等である。

一方、`force` のタグで見ると、care / structure がやや多く、connect が少なめに見える。これは11役割の構造上の結果でもあるが、結果ページで `centerForce` を強く見せる場合は、5つの力の出方に偏り感が出ないか確認が必要である。

質問文は全体的にポジティブで、回答しやすい。反面、「大切にする」「得意だ」「価値を感じる」「社会に必要」など、望ましい回答に見えやすい語が多い。ユーザーが「こう答えた方がよさそう」と感じると、診断結果の納得感が下がる可能性がある。

rare役割に近い `revolist` / `crazist` は、強い行動性や独自性を問う文が多い。自信がある人には刺さるが、控えめな参加者は実際に近い特性を持っていても選びにくい可能性がある。

### 設問改善の方向性

- 「大切にする」「得意だ」を減らし、具体場面での自然な行動を問う
- 社会的に望ましい一般論ではなく、選び方の違いが出る文にする
- rare役割は強い自己主張だけでなく、小さな違和感や別案を置く行動でも測る
- 類似質問は役割の別側面を測るように差をつける
- 5つの力を結果に強く出すなら、force分布の見え方も再点検する

## E. 11役割判定の納得感

### 現状

`calculateIcebreakResult.ts` は、33問の回答から `roleScores` と `forceScores` を計算し、`judgeRoleResult` を経由して `mainTypeKey` を決めている。`partnerTypeKey` は `slotForce` をもとに `choosePartner` で選ばれ、`thirdTypeKey` は `futurePartners` も参照して選ばれる。

つまり、11役割判定自体は内部に存在している。しかし結果ページでは、11役割名よりも「入口」「中心の力」「今日の動き方」が前面に出るため、ユーザーが「自分はこの役割だ」と持ち帰るには少し弱い。

### 納得感を上げるために必要なこと

- 「あなたがこの役割になった理由」を短く表示する
- 上位2〜3役割を補助表示する
- `main role` / `partner role` / `center force` の関係を図式化する
- 11役割の短い説明を結果上部に追加する
- オフ会で名札的に使える役割名を表示する

### 注意点

役割を強く言い切りすぎると、低確信度のユーザーには違和感が出る可能性がある。そのため、低確信度時は「今日は〇〇の入口が強め」のように柔らかくしつつ、通常時は「あなたの11役割: 〇〇」を明確に出すのがよい。

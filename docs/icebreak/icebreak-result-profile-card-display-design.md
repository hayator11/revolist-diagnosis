# Icebreak 33 Result Profile Card Display Design

## 目的

Icebreak 33 / レボリスト診断の結果ページを、単なる診断結果ではなく、オフ会で見せられる自己紹介カードとして使える状態にする。

参加者が画面を見せながら、次のように自然に話せることを目指す。

```text
私は〇〇をしている人で、今回の診断では△△タイプでした。
可能性を引き出し合いやすい相手は□□タイプと◇◇タイプです。
```

現状は `mainTypeKey` / `partnerTypeKey` / `centerForce` が内部で計算されているが、結果ページ上部では「あなたの11役割」が一目で分かりにくい。`centerForce` も大きく見えるため、参加者が11役割を名札のように使いにくい。

このdocsでは、結果ページ上部に表示する情報の優先順位、自己紹介カード、2タイプ表示、入力項目、保存方針を整理する。今回は設計docsのみで、実装は行わない。

## 結果ページ上部の優先表示

結果ページ上部では、次の順で情報を見せる。

1. あなたの11役割
2. 役割の短いキャッチコピー
3. 自己紹介カード
4. 可能性を引き出し合いやすい相手 2タイプ
5. `centerForce` は補助情報

`centerForce` は消さない。5つの力は、11役割を理解するための補助情報として有用である。ただし、最初に見える主役は11役割にする。`centerForce` は「この役割が今日どんな入口で出ているか」を補足する位置へ下げる。

## 「あなたの11役割」表示案

結果ページ上部に、役割を名札として使える表示を置く。

```text
あなたの11役割

〇〇タイプ
一言キャッチコピー

あなたは、△△を自然に担いやすい人です。
```

通常表示:

```text
あなたの11役割は、〇〇タイプです。
```

低確信度時:

```text
今日は、〇〇タイプの入口が強めに出ています。
```

強く決めつけすぎないが、オフ会で使える程度には明確にする。低確信度の場合も「まだ分からない」だけで終わらせず、今日の会話の入口として使える役割名を表示する。

### 表示に使う候補データ

- `result.mainTypeKey`
- `revo111Roles[result.mainTypeKey].name`
- `icebreakRoleResultCopy[result.mainTypeKey].catchCopy`
- `icebreakRoleResultCopy[result.mainTypeKey].workingCopy`
- `result.roleScores` の上位候補
- `result.centerForce`

`roleScores` の上位2〜3件は、納得感を補う補助表示として使える。ただし、上部の主役は `mainTypeKey` の11役割にする。

## 自己紹介カード表示案

結果ページには、参加者がそのまま見せられる自己紹介カードを置く。

基本形:

```text
今日の私は、〇〇タイプ。
□□をしている人です。

今日ここにいるきっかけは、△△です。

可能性を引き出し合いやすい相手は、
◇◇タイプ / ☆☆タイプ。
```

少し会話向きにする場合:

```text
私は、□□をしている人です。
今日ここに来たきっかけは、△△です。

今回の診断では、
「〇〇タイプ」でした。

お互いの可能性を引き出し合いやすい相手は、
「◇◇タイプ」と「☆☆タイプ」です。
```

短く見せる場合:

```text
今日の私は、〇〇タイプ。
□□をしている人です。

可能性を引き出し合いやすい相手は、
◇◇タイプ / ☆☆タイプ。
```

### 本人入力がない場合

何をしている人かが未入力:

```text
今日の私は、〇〇タイプ。
```

今日ここにいるきっかけが未入力:

```text
今日はこのタイプを入口に話してみてください。
```

未入力項目は空欄として見せない。カードが穴あきに見えると会話しづらくなるため、未入力項目は非表示にするか、診断結果だけで成立する短い文へ切り替える。

## 入力項目の扱い

入力項目の優先順位は次の通り。

必須:

- ニックネーム

任意:

- 何をしている人ですか？
- 今日ここにいるきっかけは？

初期優先度を下げる項目:

- 今日話したいこと

`今日話したいこと` は少し硬く、初対面では答えづらい可能性がある。`今日ここにいるきっかけ` の方が自然に会話へ入りやすい。

### 入力タイミング案

案A: 診断前に入力

- メリット: 診断後すぐ自己紹介カードが完成する
- 注意: 入力項目が増えると診断開始前の負荷が上がる

案B: 診断後に入力

- メリット: 結果を見た後なので、カードを整える意図が伝わりやすい
- 注意: 入力せず離脱する参加者がいる

案C: 初期はニックネームのみ、任意項目は後続Phase

- メリット: 既存導線への影響が小さい
- 注意: 自己紹介カードとしては情報が薄くなる

初期実装は案Cまたは案Bが安全である。オフ会現場で使う場合は、診断後に軽く追加入力できる方が自然に見える。

## 可能性を引き出し合いやすい相手 2タイプ表示

第一候補の見出し:

```text
可能性を引き出し合いやすい相手
```

補助表現:

```text
お互いの可能性を引き出し合いやすい相手
お互いの持ち味が活きやすい相手
次の一歩が見えやすい相手
一緒に話すと、形になりやすい相手
会話のきっかけになりやすい相手
```

避ける表現:

```text
話すと広がりやすい相手
相性がいい人
あなたに合う人
弱点を補う人
この人と組むべき
```

`相性がいい人` は恋愛的に見える可能性があり、人間関係を固定する印象も出やすい。レボリスト診断では、上下関係や依存ではなく、応援、持ち寄り、可能性を引き出し合う関係として表現する。

### 2タイプ選出の初期方針

1タイプ目:

- `partnerTypeKey`

2タイプ目:

- `revo111Roles[mainTypeKey].futurePartners`
- または `teamCompatibility` の `best` / `good`

新しい判定ロジックを増やしすぎず、既存の `partnerTypeKey` と既存相性データを活用する。

候補整理ルール:

- `partnerTypeKey` を1タイプ目に置く
- 2タイプ目は `futurePartners` から優先して選ぶ
- `teamCompatibility` に `best` / `good` がある場合は候補に入れる
- 候補が重複する場合は重複を除く
- 本人の `mainTypeKey` と同じ役割が出る場合は別候補へ回す
- 候補が1タイプしか出せない場合は、無理に2タイプ目を作らず1タイプ表示にする

### 表示文言候補

```text
可能性を引き出し合いやすい相手は、
〇〇タイプと□□タイプです。
```

```text
この2タイプは、あなたの持ち味が会話の中で出やすくなる相手です。
```

```text
「合う・合わない」を決めるものではなく、
今日の会話のきっかけとして使ってください。
```

```text
見かけたら、どんなきっかけで来たのか聞いてみてください。
```

断定しすぎず、会話の入口として使える表現にする。

## centerForce の扱い

`centerForce` は、結果ページ上部の主役にはしない。11役割を見せた後に、今日の入り方や会話の入口として補助表示する。

表示例:

```text
今日の入口になっている力
〇〇

この力は、あなたの〇〇タイプが今日どんな形で出やすいかを示しています。
```

`centerForce` を補助情報に下げることで、結果ページが「5つの力診断」に見えることを避ける。

## host画面との接続

この設計は結果ページだけで完結させず、後続のhost画面改善にもつなげる。

host画面の参加者カードに表示する候補:

- ニックネーム
- 11役割名
- 何をしている人か
- 今日ここにいるきっかけ
- 可能性を引き出し合いやすい相手 2タイプ
- `centerForce`

host画面では、運営者が席順や声かけの判断に使いやすいように、11役割名を先に見せる。`centerForce` はサブ情報として残す。

今回のdocsではhost画面実装は行わない。

## 保存方針の注意

以下の自由記述項目は、個人情報に近い扱いになる可能性がある。

- 何をしている人か
- 今日ここにいるきっかけ

これらはイベント運営用の一時データとして扱う。

- 長期保存しない
- 匿名統計には入れない
- イベント終了後3日で削除対象にする
- host画面や参加者表示に出す場合は、参加者が入力内容を理解できるUIにする

### DB対応候補

案A: `result_summary jsonb` に profile 情報を入れる

- 既存カラムを使える
- ただし診断結果と自己紹介情報が混ざりやすい

案B: `icebreak_event_participants` に `profile jsonb` を追加する

- 責務が分かりやすい
- DBスキーマ変更が必要

案C: まずは結果ページ上だけに表示し、DB保存は後回しにする

- 既存DBに影響しない
- host画面へ展開できない

初期は案Cまたは案Aを検討する。ただしhost画面へ表示するなら、保存期間と削除対象を明確にした上で案Bも検討する。

## 実装優先順位案

### Phase 1: 結果ページ上部に「あなたの11役割」を明確表示

- `mainTypeKey` の役割名を上部へ出す
- キャッチコピーを添える
- `centerForce` は補助情報へ移動する
- 既存結果ページの導線を壊さない

### Phase 2: 可能性を引き出し合いやすい相手 2タイプ表示

- 1タイプ目は `partnerTypeKey`
- 2タイプ目は `futurePartners` または `teamCompatibility` の `best` / `good`
- 重複除外と本人役割除外を入れる
- 表現は「会話のきっかけ」として扱う

### Phase 3: 自己紹介カード表示

- ニックネームと11役割を使ったカードを出す
- 任意項目がなくても成立する表示にする
- 共有やスクリーンショットに耐える短い構成にする

### Phase 4: 診断前または診断後に任意入力欄を追加

- 何をしている人ですか？
- 今日ここにいるきっかけは？
- `今日話したいこと` は初期優先度を下げる

### Phase 5: host画面の参加者カードへ展開

- 11役割名をhost画面に表示
- 可能性を引き出し合いやすい相手 2タイプを表示
- 自由記述を出す場合は保存期間と表示範囲を明確にする

## 推奨結論

結果ページ上部は、まず「あなたの11役割」を主役にする。`centerForce` は消さず、11役割の補助情報として下げる。

自己紹介カードでは、参加者がそのまま読める短い文を用意する。入力項目はニックネームを必須にし、任意項目は「何をしている人ですか？」「今日ここにいるきっかけは？」を優先する。

相手候補の見出しは「可能性を引き出し合いやすい相手」を第一候補にする。2タイプ表示は `partnerTypeKey` と既存の `futurePartners` / `teamCompatibility` を使い、新しい判定ロジックを増やしすぎない。

実装は、結果ページ上部の11役割表示から小さく始めるのが安全である。
